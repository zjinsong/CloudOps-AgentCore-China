# 十、质量评估：不只看能不能返回文字

中国区当前不提供托管 AgentCore Evaluations，本项目使用离线测试、固定题集和云端只读验收。下面是完整的实施规划；自动语义评分平台尚未包含在仓库中。

## 评什么

| 维度 | 判定例子 |
| --- | --- |
| 路由 | EC2 CPU 应交 Monitoring，不交 FinOps |
| 参数 | 区域、时间范围、资源 ID、统计口径正确 |
| 覆盖 | 是否分页穷尽；截断/无权限有明确说明 |
| 事实 | 表格数值与工具返回一致，不杜撰实例费用 |
| 协作 | 依赖顺序正确，独立步骤能并行，失败分支可解释 |
| 恢复 | 页面断开、Worker 重启后任务可追踪，无重复最终答复 |
| 安全 | 禁止调用写业务 API，不泄露 Secret |
| 性能 | 成功率、P50/P95 延迟、模型调用次数、成本 |

## 第一阶段：离线规则与数据

整理至少 30 个脱敏题目，每题保存 prompt、能力约束、固定工具返回和验收条件。包括正常 EC2、无资源、CloudTrail 多页、指标无数据、模型超时、工具失败、显式指定专家和不指定专家。

例如：

```json
{
  "id": "ec2-audit-pagination",
  "prompt": "检查宁夏区实例最近24小时关机操作",
  "required_experts": ["monitoring", "cloudtrail"],
  "checks": ["resource_discovery", "all_event_pages", "instance_id_match", "no_invented_event"],
  "fixture": "sanitized-two-page-events"
}
```

这些字段是建议的评估数据格式，不是当前 API。先用程序判数值、资源 ID、页覆盖和非法工具；开放语义结论由人工复核，避免只让另一个模型给分。

## 第二阶段：云端只读题集

在测试账号创建少量已知资源与可核对的审计事件，固定时间窗，重复运行每题。记录代码 commit、镜像、Runtime 配置版本、模型 ID、提示词、工具 Schema、trace/task ID、结果、调用次数与耗时。

用 AWS CLI/控制台结果作为对照，不能用 Agent 自己的结论当真值。实际云数据会变化，应保存查询时间和脱敏证据。

## 第三阶段：变更发布门槛

更换模型、提示词、工具或 harness 时先跑同一批离线题，再跑云端题。建议门槛：安全违规与编造关键事实必须为零；必需路由与页覆盖全部通过；成功率和 P95 不明显退化；人工验收关键客户题。

门槛值依据基线确定，不先编造“95%准确率”。评估失败应定位到计划、权限、网络、工具数据或汇总层，再决定修复与发布。

## 实施顺序

1. 建题集和人工验收表。
2. 增加工具 fixture 与可重复离线运行器。
3. 增加事实/覆盖规则评分和结果 JSON。
4. 关联现有 task/trace，在观测页面显示版本与验收状态。
5. 接入 CI 离线门槛，云端验收作为受控发布步骤。

现有 `tests/` 已覆盖状态机、权限、部分失败和接口契约，不能当成完整答案质量评估。
